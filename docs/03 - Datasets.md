## Overview

All public datasets come from **Loghub** (logpai/loghub on GitHub — it links to the Zenodo downloads). Numbers below are from the Loghub paper and the ICSE 2022 empirical study.

| Dataset | Source system | Log lines | Anomalies | Anomaly share | Grouping |
|---|---|---|---|---|---|
| HDFS_v1 | Hadoop file system, 200+ nodes | 11,175,629 | 16,838 anomalous blocks (of ~575k) | 2.93% of blocks | Session by `block_id` |
| BGL | Blue Gene/L supercomputer | 4,747,963 | 348,460 alert lines | 7.34% of lines | Fixed / time windows |
| Loghub-2k | 16 systems, 2,000 lines each | 2,000 per system | — | — | Ground-truth templates for parser accuracy |
| Demo app | Our microservices | as many as we generate | from fault-injection log | we control it | Session by `trace_id` |

## HDFS

**What it is:** logs from a Hadoop cluster running MapReduce jobs. Every line about a data block contains its ID, e.g. `blk_-1608999687919862906`.

Example lines:

```
081109 203615 148 INFO dfs.DataNode$PacketResponder: PacketResponder 1 for block blk_38865049064139660 terminating
081109 203807 222 INFO dfs.DataNode$PacketResponder: Received block blk_-6952295868487656571 of size 67108864 from /10.251.42.84
```

**Files you get:** `HDFS.log` (~1.5 GB) and `preprocessed/anomaly_label.csv` (`BlockId,Label` with `Normal` / `Anomaly`).

**How we use it:**
- Regex `blk_-?\d+` → session ID. One line can mention more than one block; attach the event to every block found.
- Label per session from `anomaly_label.csv`.
- Sort sessions by their first timestamp → chronological split.

**Why it's the main benchmark:** clean sessions, reliable labels, ~30–50 templates. Almost every paper reports on it, so our numbers are comparable.

**Caveat to mention in the report:** HDFS is "easy" — most methods score F1 > 0.9 on it, so it doesn't separate good methods from great ones. That's why we add BGL.

## BGL

**What it is:** logs from the Blue Gene/L supercomputer at Lawrence Livermore National Lab.

Example line:

```
- 1117838570 2005.06.03 R02-M1-N0-C:J12-U11 2005-06-03-15.42.50.675872 R02-M1-N0-C:J12-U11 RAS KERNEL INFO instruction cache parity error corrected
```

The **first column** is the label: `-` means normal; anything else (e.g. `APPREAD`, `KERNDTLB`) is an alert category → anomalous.

**How we use it:**
- No session ID, so build windows: fixed-count (20 / 100 lines) and/or time-based (e.g. 1 h windows with 30 min step).
- A window is anomalous if it contains at least one anomalous line.
- Chronological split is critical here — the ICSE 2022 study found DeepLog F1 on BGL drops from 0.927 (random split) to 0.426 (chronological). BGL also has many templates that only appear later in time.

## Loghub-2k labelled samples

2,000 lines per system with hand-labelled templates. Use HDFS-2k and BGL-2k to:
- measure **parsing accuracy** (grouping accuracy) of Drain,
- tune `sim_th` and the masking regexes before running on the full logs.

## Our own demo-app dataset

Generated by [[06 - Microservices Demo Setup]].

| Phase | How long | Content | Label |
|---|---|---|---|
| Normal run | 2–3 hours of load | Only healthy traffic | All normal → DeepLog training data |
| Fault run | 1–2 hours | Normal traffic + scheduled faults | Sessions overlapping a fault window and touching the faulty service → anomalous |
| Held-out run | 30–60 min, different seed | Same fault types, different timing | Test set for live evaluation |

The fault injector writes a ground-truth file:

```csv
fault_id,type,target_service,start_ts,end_ts
f01,latency_2000ms,payment,2026-11-20T10:05:00Z,2026-11-20T10:07:00Z
f02,kill,inventory,2026-11-20T10:20:00Z,2026-11-20T10:21:30Z
```

Labelling rule (write it down in the report): a trace is anomalous if it started inside `[start_ts, end_ts + grace]` and touched `target_service`. Also keep a small set of hand-checked traces to sanity-check the rule.

**Publish it.** A small, documented microservice log dataset with trace IDs and fault labels is a genuine contribution — put it on GitHub/Zenodo with a README.
